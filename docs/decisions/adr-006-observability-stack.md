# ADR-006 관측 스택: 자체 운영 Prometheus + Grafana

상태: **Accepted**

스택 자체는 2026-05-07부터 운영 중이었고 근거가 문서로 남아 있지 않았다. 이 문서가 그 선택을 기록하고, 운영하면서 드러난 미비점을 후속 과제로 분리한다.

## 배경

자동 게시는 HTTP 요청 없이 스케줄러로 돈다. 그래서 웹 계층 지표(`http.server.requests`)로는 이 경로의 상태를 알 수 없다. 매시 실행이 전부 실패해도 서버 지표는 정상으로 보인다.

여기에 실패 격리가 겹친다. `LaunchNewsPublishScheduler`는 키워드 하나가 실패해도 WARN 로그만 남기고 다음 키워드로 넘어간다. 이 설계는 배치 전체가 멈추는 것을 막지만, 대신 실패가 조용해진다. 로그는 상시 감시 대상이 아니므로 사람이 "며칠째 새 글이 없다"를 눈으로 발견하기 전까지 아무도 모른다.

외부 의존성이 셋이고 실패 방식이 서로 다르다.

| 의존성 | 대표 실패 | 앱에서 보이는 모습 |
|---|---|---|
| 네이버 API HUB | 429 쿼터 초과, 401 키 만료 | 예외 후 키워드 건너뜀 |
| LLM 게이트웨이 | 타임아웃, 빈 응답 | `AI_GENERATION_FAILED` skip |
| pgvector | 적재·검색 실패 | 503 또는 게시 중단 |

네이버 쿼터는 특히 되돌릴 수 없다. 검색 카테고리 합산 월 775,000건을 소진하면 그달 남은 기간 전체가 죽는다. 소진된 뒤에 아는 것과 접근하는 중에 아는 것의 차이가 크다.

## 결정

**자체 운영 Prometheus + Grafana를 쓰고, 앱은 지표를 노출만 한다.**

```
앱 호스트                            모니터링 호스트
  애플리케이션                          Prometheus  ──15초 pull──┐
    /actuator/prometheus  ◄─────────────────────────────────────┘
    베이직 인증                          Grafana ── Prometheus 조회
            └──────────── VPN 사설 대역 ────────────┘
```

- **pull 방식.** 앱은 모니터링 서버 주소를 모른다. 엔드포인트만 열어 두고 대상 목록은 `prometheus.yml` 한 곳에서 관리한다. 긁기 실패 자체가 `up` 지표로 남는다.
- **compose 파일 분리.** 호스트가 다르므로 배포 스택과 관측 스택을 나눈다. 한 파일이면 모니터링 호스트에서 앱까지 올리려 든다. 배포 스택은 이 저장소의 `docker-compose.prod.yml`이고, 관측 스택은 모니터링 호스트의 별도 디렉터리에 있다.
- **VPN 경유.** 액추에이터를 공개 인터넷에 노출하지 않고 사설 대역에서만 접근한다. 베이직 인증은 그 위의 두 번째 방어선이다.

계측은 네 축으로 나눠 각 단계를 분리해 본다. 파이프라인이 느려졌을 때 어느 단계인지 좁히기 위함이다.

| 단계 | 지표 접두어 |
|---|---|
| 뉴스 수집 | `external_naver_fetch` |
| 벡터 적재 | `external_source_db_persist`, `ingest_documents_embeddings` |
| RAG 검색 | `ai_vector_search` |
| LLM 생성 | `ai_text_generation` |

각 축은 호출 수, 실패 수, 소요 시간을 갖춘다. 여기에 수집 축만 `external_naver_fetch_items_total`을 추가로 센다. **호출은 성공했는데 결과가 0건인 상태**를 잡기 위해서다. 네이버가 응답 필드명을 바꾸면 200이 오고 파싱은 조용히 빈 리스트를 만든다. 호출 수와 결과 수를 따로 세지 않으면 이 실패는 지표상 완전히 정상으로 보인다.

## 다른 선택지를 고르지 않은 이유

**관측 없이 운영한다.** 가장 싸지만 위의 배경이 그대로 사고가 된다. 스케줄러가 조용히 실패하는 구조에서 지표가 없으면 발견이 며칠 단위로 늦는다. 네이버 쿼터는 소진 후에 알면 복구 수단이 없다.

**SaaS(Datadog, New Relic 등)를 쓴다.** 지표·로그·추적을 묶어 주고 설정이 짧다. 그러나 비용이 사용량에 비례하고, 개인 프로젝트에서 호스트 두 대에 붙이는 비용으로는 정당화되지 않는다. 그리고 지표가 외부로 나간다. 자체 운영은 컨테이너 두 개와 설정 파일 두 개가 전부라 운영 부담이 SaaS 비용보다 작다.

**로그만으로 대응한다.** 이미 구조화 로그가 있으니 추가 도구가 필요 없다. 그러나 로그는 "무슨 일이 있었나"에 답하고 "얼마나 자주, 얼마나 오래"에는 답하지 못한다. 실패율 추이나 p95 지연을 로그에서 계산하려면 결국 집계 계층을 따로 만들어야 하고, 그건 지표 도구를 다시 만드는 일이다. 두 축은 대체재가 아니라 보완재다.

**ELK나 Loki를 중심에 둔다.** 로그 검색에는 우수하지만 같은 이유로 지표 질문에 약하다. 그리고 Prometheus보다 무겁다. 로그 검색이 필요해지면 Loki를 Grafana에 데이터소스로 추가하는 경로가 열려 있으므로, 지금 먼저 도입할 이유가 없다.

**앱에서 push한다(StatsD, Pushgateway).** push는 짧게 살다 죽는 프로세스에 필요하다. 이 프로젝트의 스케줄러는 장기 실행 애플리케이션 안에서 돌기 때문에 해당되지 않는다. push를 쓰면 앱이 모니터링 서버 주소와 자격증명을 알아야 하고, 전송 실패를 앱이 처리해야 한다. pull은 그 결합을 없앤다.

**분산 추적(Jaeger, Tempo)을 함께 도입한다.** 추적은 서비스 여러 개를 거치는 요청에서 값어치가 있다. 지금은 모듈러 모놀리스라 한 프로세스 안에서 끝난다([ADR-003](./adr-003-modular-monolith.md)). 서비스를 분리하는 시점에 다시 판단한다.

## 영향

- 앱은 `spring-boot-starter-actuator`와 `micrometer-registry-prometheus`만 의존한다. 관측 도구를 바꿔도 앱 코드는 바뀌지 않는다.
- 지표 이름과 태그가 앱 코드 밖의 계약이 된다. `application-monitoring.yml`의 히스토그램·SLO 설정, [성능 문서](../performance/README.md)의 지표 표, Grafana 패널이 모두 이 이름에 의존한다. 이름을 바꾸면 세 곳이 함께 깨진다. `NaverNewsSourceClientTest`가 미터 이름과 태그를 단언해 이 계약을 고정한다.
- 보존 기간이 Prometheus 기본값 15일이다. 그보다 오래된 원본 데이터는 자동 삭제되므로, 장기 비교가 필요한 측정은 요약을 문서로 따로 남긴다.
- 액추에이터 엔드포인트가 인증 뒤에 있으므로 스크레이프 설정에 자격증명이 필요하다.

## 후속 과제

**관측 스택 설정이 버전 관리되지 않는다.** 모니터링 호스트의 compose 파일과 `prometheus.yml`이 어떤 저장소에도 없다. 스크레이프 대상, 인증 설정, 컨테이너 구성이 그 머신의 파일에만 존재한다. 머신이 죽으면 지표 원본(보존 15일)뿐 아니라 그것을 다시 세울 방법까지 함께 사라진다. 아래 두 과제보다 이것이 먼저다.

**대시보드를 코드로 관리한다.** 현재 Grafana 대시보드는 `grafana_data/grafana.db` 안에만 있다. `provisioning` 디렉터리는 마운트돼 있으나 비어 있다. 이 상태의 문제는 이미 한 번 관측됐다. [성능 결과 문서](../performance/results.md)에 "과거 Grafana 메모의 `Duration MAX=182ms`는 panel metric 정의가 보존되지 않아 비교표에서 제외했다"는 기록이 있다. 패널 정의가 남지 않아 과거 측정치를 쓸 수 없게 된 사고다. 대시보드와 데이터소스를 JSON·YAML로 내보내 저장소에 두면 복구·리뷰·영향 범위 검색이 모두 가능해진다.

**알림 규칙이 없다.** 지표는 쌓이지만 임계를 넘었을 때 알려 주는 장치가 없다. 우선순위는 네이버 429 지속과 스케줄러 무응답이다. 앞의 것은 쿼터 소진 임박, 뒤의 것은 자동 게시 중단을 뜻한다.

**호스트·컨테이너 자원 지표가 없다.** 지금은 애플리케이션이 스스로 보고하는 값만 있다. CPU·메모리·디스크를 보려면 node_exporter와 cAdvisor를 스크레이프 대상에 추가해야 한다. 성능 문서가 요구하는 관측값 중 이 부분이 비어 있다.

**Grafana 노출 범위가 Prometheus와 다르다.** Prometheus는 VPN 주소에만 바인딩하는데 Grafana는 모든 인터페이스에 열려 있다. 관리자 자격증명도 compose 파일에 평문으로 있다. 바인딩을 Prometheus와 같은 정책으로 맞추고 자격증명을 환경변수로 빼야 한다.
