# Nginx 502/504

## 의미

| 상태 | 일반적인 의미 |
| --- | --- |
| 502 Bad Gateway | Nginx가 upstream app에 연결하지 못했거나 upstream이 유효하지 않은 응답을 반환했다. |
| 504 Gateway Timeout | Nginx는 upstream에 연결했지만 proxy timeout 안에 응답을 받지 못했다. |

PostForge backend는 Spring Boot로 실행되며 PostgreSQL과 Redis에 의존한다.
Docker 배포에서는 DB와 Redis container가 healthy가 된 뒤 app이 시작되어야 하며, 이후 `/actuator/health`가 `UP`을 반환해야 한다.

## 1차 확인

1. app container/process가 실행 중인지 확인한다.
2. Nginx를 우회해 backend port에서 `GET /actuator/health`를 직접 호출한다.
3. Nginx upstream host와 port를 확인한다. compose network에서는 보통 `localhost`가 아니라 service name과 app port를 쓴다.
4. app log에서 startup failure, DB connection failure, Redis connection failure, port binding error를 확인한다.
5. Nginx error log에서 `connect() failed`, `upstream timed out`, `connection refused`를 확인한다.
6. PostgreSQL과 Redis healthcheck가 healthy인지 확인한다.

## 502일 때 먼저 의심할 것

연결성 또는 process 문제를 먼저 본다.

- app process가 crash 되었거나 시작되지 않았다.
- Nginx가 잘못된 upstream name/port를 가리킨다.
- container network와 Nginx network가 다르다.
- Nginx와 app 사이에 TLS가 설정되어 있지만 app은 plain HTTP로 응답한다.
- app이 요청 처리 중 종료되어 malformed response를 반환한다.

## 504일 때 먼저 의심할 것

느린 요청 경로 또는 의존성 대기를 먼저 본다.

- 로그인 요청은 BCrypt가 request path에서 실행되므로 CPU-heavy하다.
- DB query regression이 생겼다. 특히 `GET /posts` N+1 또는 batch/fetch tuning 누락을 확인한다.
- 외부 API, SMTP, OpenAI, vector store 호출이 동기 경로에 있다.
- Redis 또는 DB command latency가 높다.
- proxy timeout이 가장 느린 정상 요청보다 짧다.

## 복구

- 먼저 직접 app health를 회복한 뒤 Nginx 경로를 확인한다.
- direct health가 down이면 Nginx보다 app dependency 또는 configuration을 먼저 고친다.
- direct health는 up인데 Nginx만 실패하면 upstream routing, network, header, timeout 설정을 고친다.
- 특정 endpoint만 504라면 k6/Grafana와 app log로 느린 route를 분리한다.
